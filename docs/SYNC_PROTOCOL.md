# 远程同步协议草案

> 当前版本不支持远程同步或错题社区。`server/` 是历史实现，与当前数据库模型不兼容，不能作为受支持的同步服务器部署或连接。本文只记录未来实现必须满足的约束，不描述可用功能。

## 当前状态

- 客户端同步页只显示停用说明，不进行网络请求。
- `/community` 重定向到同步停用说明；远程发布、撤销和浏览接口已移除。
- 本地仍保留 `version`、`sync_status`、`deleted_at` 等元数据，用于数据生命周期和未来协议演进。
- `server/app.py` 未适配规范化数据库，不在当前测试、构建或发布支持范围内。

跨设备迁移目前应使用 JSON 导出和导入。

## 未来实现的强制约束

### 记录标识

记录身份必须使用 `(table_name, id)` 复合键。不同表允许出现相同 UUID，服务端、握手算法、上传、下载和冲突记录均不得只以 `id` 定位记录。

客户端与服务端必须共享明确的表名映射，至少覆盖：

1. `subjects`
2. `sources`
3. `error_questions`
4. `srs_data`
5. `attachments`
6. `error_tags`

### 关系数据

附件和标签是多对多资源。同步负载必须以完整、排序且去重的 `question_ids: string[]` 表示关系集合，不能降级为单个 `question_id`。

- 应用远端记录时，本地关系集合应与负载精确一致。
- 从一个问题删除附件或标签只解除该关系。
- 仅在最后一条关系解除后，资源本身才设置 `deleted_at`。
- 删除问题时，应解除该问题的所有关系；仍被其他问题引用的资源必须保留。

### 依赖顺序与引用完整性

拉取和应用数据必须遵循：

`subjects → sources → error_questions → srs_data / attachments / error_tags`

不得静默丢弃引用不存在问题的 SRS 数据。遇到孤立 SRS 或无法满足的父级引用时，整批操作必须报错并回滚，错误中应包含可定位的记录 ID。

### 版本规则

- 客户端本地修改只设置 `sync_status = pending`，不得自行增加服务端版本。
- 服务端接受写入后生成单调递增的新版本，并将该版本返回客户端。
- 删除使用 `deleted_at` 传播，仍遵守相同版本规则。
- 冲突比较必须基于同一个 `(table_name, id)` 的版本，不能跨表比较。

### 原子性

一次远端批次的实体写入、关系集合更新和同步元数据更新必须处于同一事务。任何记录失败都应回滚整个批次，不能留下部分规范化数据。

## 重新启用条件

远程同步和社区入口只有在以下条件全部满足后才能重新启用：

1. 新服务端实现上述数据契约，并完成协议版本协商。
2. 客户端具备不兼容协议的显式拒绝路径。
3. 覆盖复合键、多对多解绑、软删除、孤立引用、冲突和事务回滚的端到端测试通过。
4. 用户文档、部署文档和安全配置针对新实现重新审核。

在此之前，历史服务端不提供兼容性或数据安全保证。
